프로젝트 소개

React2Shell (CVE-2025-55182)은 React Server Components(RSC)의 Server Function 요청 역직렬화 과정에서 발생하는 원격 코드 실행 취약점입니다. 본 프로젝트에서는 Next.js 15.0.0 기반의 취약 애플리케이션을 구성하고, Flight Protocol로 전달되는 직렬화 데이터가 서버 런타임에서 어떻게 처리되는지 분석했습니다.

단순히 공개 취약점 개요를 정리하는 데 그치지 않고, RSC 요청 흐름, Server Action 호출 구조, 객체 속성 오염 가능성, Node.js 런타임 명령 실행 흐름을 단계별로 검증했습니다. 이후 패치 버전 식별, WAF/프록시 임시 완화, 런타임 권한 최소화, 비밀값 교체, 로그 기반 침해 점검까지 운영 환경 대응 관점으로 정리했습니다.

기획 의도

  • React Server Components와 Flight Protocol이 클라이언트-서버 경계에서 데이터를 직렬화·역직렬화하는 방식을 분석했습니다.
  • Next.js App Router 환경에서 Server Function 요청이 어떤 조건에서 공격 표면으로 노출될 수 있는지 확인했습니다.
  • RCE뿐 아니라 Server Action 소스 노출, 순환 역직렬화 DoS 등 연계 위험을 함께 검토했습니다.
  • React/Next.js 패치, 임시 차단 정책, 런타임 격리, 사후 침해 점검을 포함한 실무 대응 방안을 정리했습니다.

수행 역할

  • Vulnerability Analysis: Next.js 15.0.0의 RSC 처리 흐름과 Flight 데이터 역직렬화 과정을 분석하고, 사용자 제어 입력이 서버 측 객체 처리 경로로 전달되는 구조를 확인했습니다.
  • Environment Build: React 19, Next.js 15, Node.js 20 기반의 Docker 재현 환경을 구성하고, '/vulnerabilities/rce' 엔드포인트에서 검증 가능한 테스트 화면을 구현했습니다.
  • Verification: Proxy 도구로 조작된 Flight/JSON 요청을 전송하고, 'id', 'whoami' 등 명령 실행 결과를 통해 서버 런타임 권한에서 RCE 흐름이 성립하는지 확인했습니다.
  • Documentation: 웹 서버 접근, 정상 요청 확인, 페이로드 주입, 실행 결과 확인, 대응 방안까지 Step 기반으로 정리하고 포트폴리오용 캡처 이미지를 함께 구성했습니다.

주요 성과 및 인사이트

  • 최신 프론트엔드 프레임워크 기능도 서버 런타임과 연결되는 순간 백엔드 RCE 공격 표면이 될 수 있음을 확인했습니다.
  • Flight Protocol 요청이 정상 RSC 트래픽처럼 보일 수 있어, 단순 문자열 차단보다 패치와 요청 정규화 기반 탐지가 중요하다는 점을 정리했습니다.
  • React RSC 패키지와 Next.js 릴리스 라인별 패치 버전을 구분하고, 취약한 'next@15.0.0' 환경의 업그레이드 기준을 명확히 정리했습니다.
  • 컨테이너 non-root 실행, 읽기 전용 파일 시스템, 아웃바운드 통신 제한, 비밀값 교체 등 취약점 악용 이후의 피해 범위를 줄이는 운영 대응 방안을 도출했습니다.

프로젝트 소개

Spring4Shell (CVE-2022-22965)은 Spring Framework의 데이터 바인딩 과정에서 'class.module.classLoader'와 같은 속성 경로가 노출되며 발생하는 원격 코드 실행 취약점입니다. 본 프로젝트에서는 Spring MVC의 객체 바인딩 흐름과 Java 9+ 'Module' 속성 접근 구조를 분석하고, Tomcat의 'AccessLogValve' 설정 조작이 웹 루트 내 JSP 파일 생성으로 이어지는 과정을 재현했습니다.

단순히 공개 PoC를 실행하는 방식이 아니라, 취약한 WAR 배포 환경을 Docker로 구성하고 Burp Suite를 통해 요청 파라미터가 서버 런타임 설정에 반영되는 흐름을 단계별로 확인했습니다. 이후 생성된 JSP가 실제로 서버 권한에서 실행되는지 검증하고, 패치·임시 완화·운영 탐지 관점의 대응 방안을 보고서 형태로 정리했습니다.

기획 의도

  • Spring DataBinder가 HTTP 파라미터를 객체 속성에 매핑하는 과정에서 어떤 경로가 노출될 수 있는지 분석했습니다.
  • Java 9 이상에서 추가된 'module' 속성을 통해 'ClassLoader' 접근이 가능해지는 조건을 확인했습니다.
  • Tomcat 'AccessLogValve'의 로그 경로, 파일명, 확장자, 패턴 설정이 런타임에서 조작될 때 어떤 위험이 발생하는지 검증했습니다.
  • Spring Framework 패치, Tomcat 임시 완화, WebDataBinder 차단, WAF 탐지 등 실무 대응 관점까지 함께 정리했습니다.

수행 역할

  • Vulnerability Analysis: 'VulnController'의 '/vulnerability/greeting' 엔드포인트를 분석하고, 사용자 입력이 '@ModelAttribute' 바인딩 경로로 전달되는 구조를 확인했습니다.
  • Environment Build: Spring Boot 2.6.5, Spring Framework 5.3.17, Java 11, Tomcat 9.0.60 기반의 WAR 배포 환경을 Docker로 구성했습니다.
  • Verification: Burp Suite로 'class.module.classLoader' 계열 파라미터를 전송하고, Tomcat 웹 루트에 'final_poc.jsp'가 생성되는 흐름을 확인했습니다.
  • Documentation: 웹 서버 접근, 엔드포인트 확인, 페이로드 전송, 실행 결과 확인까지 Step 기반으로 정리하고 캡처 이미지를 교체할 수 있도록 문서 구조를 맞췄습니다.

주요 성과 및 인사이트

  • 객체 바인딩이라는 정상 기능이 런타임 설정 조작으로 이어질 수 있음을 코드와 요청 흐름으로 확인했습니다.
  • WAR 배포와 외장 Tomcat 조합에서 공개 PoC의 대표 공격 조건이 어떻게 성립하는지 재현 환경으로 검증했습니다.
  • 'final_poc.jsp' 실행 결과를 통해 웹 루트 파일 생성 이후 서버 측 실행 흐름이 성립하는지 확인했습니다.
  • Spring Framework 5.3.18 이상 업그레이드, Tomcat 9.0.62 이상 적용, 위험 필드 바인딩 차단, 로그 기반 탐지 등 다층 대응 방안을 정리했습니다.

프로젝트 소개

Log4Shell (CVE-2021-44228)은 Apache Log4j 2의 JNDI Lookup 기능이 신뢰할 수 없는 사용자 입력과 결합되면서 발생하는 원격 코드 실행 취약점입니다. 본 프로젝트에서는 Spring Boot 기반의 취약 애플리케이션을 구성하고, HTTP 헤더 값이 Log4j 로깅 경로로 전달되는 과정을 추적하여 JNDI Lookup이 실제 네트워크 연결 시도로 이어지는 흐름을 분석했습니다.

단순히 취약점 개요를 정리하는 데 그치지 않고, 입력 지점 식별, 취약 코드 위치 분석, Docker 기반 재현 환경 구성, 서버 로그 확인, 대응 방안 정리까지 하나의 연구 흐름으로 문서화했습니다. 포트폴리오 관점에서는 오픈소스 라이브러리 취약점이 실제 서비스의 로깅 코드와 만났을 때 어떤 방식으로 보안 경계가 무너지는지를 보여주는 대표 CVE 분석 사례입니다.

기획 의도

  • Log4j가 로그 메시지 안의 '${jndi:...}' 표현식을 어떻게 해석하는지 확인하고, JNDI Lookup이 발생하는 조건을 분석했습니다.
  • 'X-Api-Version'과 같은 HTTP 헤더 입력값이 컨트롤러를 거쳐 'logger.info()'까지 전달되는 흐름을 코드 레벨에서 추적했습니다.
  • 취약점 검증 결과를 단순 실행 성공 여부가 아니라 서버 로그, 스택트레이스, 네트워크 연결 시도 흔적 중심으로 정리했습니다.
  • 취약 버전 패치, 임시 완화, WAF/프록시 탐지, 사후 침해 점검까지 포함해 운영 환경에서 필요한 대응 관점을 함께 정리했습니다.

수행 역할

  • Vulnerability Analysis: 'Log4jVulnController'의 '/vulnerability/log' 엔드포인트를 분석하고, 사용자 입력이 필터링 없이 로깅 sink로 전달되는 구조를 확인했습니다.
  • Environment Build: Spring Boot 2.6.1, Apache Log4j 2.14.1, Java 11 기반의 Docker 재현 환경을 구성하고, 컨테이너 로그로 검증 가능한 형태로 실습 환경을 정리했습니다.
  • Verification: Burp Suite와 cURL을 활용해 조작된 'X-Api-Version' 헤더를 전송하고, 'Connection refused' 및 'com.sun.jndi.ldap.Connection.createSocket' 로그를 통해 lookup 시도를 확인했습니다.
  • Documentation: 취약점 개요, 재현 절차, 관찰 결과, 대응 방안을 'README.md'와 테스트 문서에 정리하고 보고서용 캡처 이미지를 함께 구성했습니다.

주요 성과 및 인사이트

  • 사용자 입력이 로그에 남는다는 단순한 동작이 외부 lookup으로 확장될 수 있음을 코드와 로그 흐름으로 확인했습니다.
  • 서버 응답보다 컨테이너 로그와 Java 스택트레이스가 취약점 검증에서 더 강한 증거가 될 수 있음을 정리했습니다.
  • Log4j 2.17.1 이상 업그레이드, 'JndiLookup' 제거, 아웃바운드 통신 제한, 로그 기반 침해 흔적 점검 등 다층 대응 방안을 정리했습니다.
  • 서드파티 라이브러리 취약점은 애플리케이션 코드만 보는 방식으로는 놓치기 쉽기 때문에, SBOM과 의존성 스캔을 통한 지속 관리가 필요하다는 점을 확인했습니다.

프로젝트 소개

Vuln-Camp는 Spring Boot + Next.js 기반의 이커머스 아키텍처를 직접 설계·구현한 Vulnerable-by-Design 웹 애플리케이션입니다. 상품 조회, 장바구니, 결제, 쿠폰, 고객센터(QnA), 공지사항, 마이페이지 흐름에 실제 웹 취약점 진단 시나리오를 녹여 구현했습니다.

모의해킹 결과보고서 기준 총 11건의 취약점을 진단하였으며, SQL Injection, SSRF, 파일 업로드·다운로드, 프로세스 검증 누락, 불충분한 인가, Stored XSS, CSRF, 정보 누출, 서버 정보 노출 항목에 대해 공격 절차와 보안대책을 정리했습니다.

기획 의도

단순 취약점 재현이 아니라, 설계자 겸 방어자의 시각으로 취약점이 발생하는 구조적 원인을 이해하고 실무에 적용 가능한 방어 로직을 도출하기 위해 제작했습니다. 특히 프론트엔드와 백엔드 사이의 신뢰 경계(Trust Boundary)가 결제, 쿠폰, 권한 처리 과정에서 어떻게 무너지는지를 코드와 공격 흐름으로 확인하는 데 초점을 맞췄습니다.

진단 결과

수행 역할

  • 취약점 설계 및 구현: QnA, 결제, 쿠폰, 공지사항, 파일 처리 기능에 주요 웹 취약점을 직접 구현했습니다.
  • 공격 검증: Burp Suite와 브라우저 개발자 도구를 활용해 파라미터 변조, 쿠키 변조, XSS, CSRF, SSRF, 파일 업로드·다운로드 공격을 재현했습니다.
  • 보고서 작성: 취약점별 개요, 보안 위협, 공격 절차, 증적 이미지, 보안대책을 포함한 모의해킹 결과보고서를 작성했습니다.
  • 실행 환경 구성: Docker Compose 기반으로 프론트엔드와 백엔드를 쉽게 실행할 수 있도록 구성했습니다.

주요 성과 및 인사이트

  • 공격이 성립하는 조건과 방어가 실패하는 지점을 코드 레벨에서 동시에 확인했습니다.
  • 서버가 클라이언트 값을 신뢰할 때 결제 금액 조작, 쿠폰 우회, 관리자 권한 오남용으로 이어질 수 있음을 실증했습니다.
  • 입력값 검증, 권한 검증, 파일 처리, CSRF 방어, 서버 측 비즈니스 로직 검증에 대한 보안 가이드를 정리했습니다.

프로젝트 소개

Jinwk CTF Lab은 Android Kotlin 기반으로 제작한 모바일 보안 CTF 실습 애플리케이션입니다. APK 정적 분석, 로컬 저장소 점검, 딥링크 검증, 런타임 후킹, SSL Pinning 우회, 메모리 변조 등 모바일 앱 진단에서 자주 다루는 취약점 흐름을 CTF 챌린지 형태로 구성했습니다.

총 10개의 모바일 보안 챌린지를 제작·분석하였으며, 하드코딩 계정, 안전하지 않은 로컬 저장소, 숨겨진 assets 정보, 민감 로그, 딥링크 오남용, 루팅·생체인증·SSL Pinning 우회, 메모리 변조, 암호키 추출 항목에 대해 공격 절차와 대응 방안을 정리했습니다.

기획 의도

단순 Flag 획득이 아니라, 공격자와 개발자의 시각에서 모바일 앱 취약점이 발생하는 구조적 원인을 이해하고 실무에 적용 가능한 보안대책을 도출하기 위해 제작했습니다. 특히 APK가 사용자 단말에 배포된다는 특성상 클라이언트 내부 로직, 로컬 저장소, 로그, 네트워크 검증을 신뢰 경계로 사용할 수 없다는 점을 코드와 공격 흐름으로 확인하는 데 초점을 맞췄습니다.

챌린지 구성

  • 총 챌린지: 10개
  • 분석 유형: 정적 분석 5개, 동적 분석 5개
  • 주요 항목: Hardcoded Credentials, Insecure Data Storage, Hidden Assets, Insecure Logging, Insecure Deep Link, Rooting Bypass, Biometric Bypass, SSL Pinning Bypass, Memory Modification, Crypto Key Extraction

수행 역할

  • 모바일 CTF 설계 및 구현: Kotlin 기반 Android 앱에 정적·동적 분석 챌린지를 직접 구성했습니다.
  • 공격 검증: JADX, ADB, Logcat, Frida를 활용해 APK 분석, 로컬 데이터 추출, 딥링크 호출, 런타임 후킹 시나리오를 재현했습니다.
  • 대응 방안 정리: 챌린지별 취약 원인, 공격 영향도, 개발 단계 보안대책, 운영 단계 점검 항목을 정리했습니다.
  • 배포 환경 구성: Gradle 기반 Release APK 빌드와 테스트용 APK 배포 흐름을 구성했습니다.

주요 성과 및 인사이트

  • 정적 분석과 동적 분석을 연결해 모바일 앱 취약점 진단 흐름을 전체적으로 재현했습니다.
  • 클라이언트 코드, 로컬 저장소, 로그, 딥링크, 인증 우회 로직이 실제 서비스 보안 사고로 이어지는 조건을 확인했습니다.
  • Android Keystore, 서버 측 검증, 민감 로그 제거, 딥링크 권한 검증, 런타임 변조 대응 등 모바일 보안 가이드를 정리했습니다.

프로젝트 소개

SK 쉴더스 루키즈 프로젝트는 외부 노출 자산을 식별하고, 취약점 검증부터 내부 확산 가능성 분석, 보안대책 수립까지 수행한 모의해킹 프로젝트입니다. 실제 침투 테스트 흐름에 맞춰 정보 수집, 취약점 검증, 권한 확보, 내부 자산 접근, 영향도 분석을 단계별로 진행했습니다.

Spring4Shell, TeamCity 인증 우회, Apache Struts2 파일 업로드 취약점, AI 챗봇 프롬프트 인젝션 등 총 4개의 공격 시나리오를 구성하고, 단순 패치 중심 조치가 아닌 자산관리, 비밀정보 관리, 접근통제, 배포 전 보안검증 관점의 개선 방향을 정리했습니다.

기획 의도

개별 취약점 재현에 그치지 않고, 외부 서비스 침해가 내부 시스템 접근과 데이터 노출로 확장되는 구조를 공격자 관점에서 검증하기 위해 진행했습니다. 특히 공개 웹 서비스, CI/CD 서버, 소스코드 저장소, NAS, DB, AI 챗봇이 서로 연결될 때 접근통제와 비밀정보 관리가 어떻게 보안 경계로 작동해야 하는지 분석했습니다.

공격 시나리오 및 영향

  • 공격 시나리오: Spring4Shell RCE, TeamCity 인증 우회, Apache Struts2 업로드 취약점, 챗봇 프롬프트 인젝션
  • 영향 범위: 웹서버 권한 확보, 설정 파일 접근, 소스코드 및 내부 자산 정보 확인, DB 접근 정보 노출 가능성 분석
  • 보안대책 방향: 취약 버전 패치, 외부 노출 자산 관리, Secret 관리, 내부망 접근통제, 샌드박스 기반 AI 기능 격리

수행 역할

  • AI 챗봇 시나리오 추가: Ollama 기반 챗봇을 대상으로 프롬프트 인젝션 가능성을 검증하고, 입력 통제·응답 필터링·샌드박스 격리 관점의 대응방안을 정리했습니다.
